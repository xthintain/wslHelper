# WSL截图工具项目宪章

## 核心原则

### I. 模块化优先 (Modularity-First)

每个功能模块必须独立、可测试、有明确边界。

**规则**：
- 核心功能模块（截图、路径转换、剪贴板、快捷键）必须相互独立
- 每个模块必须有清晰的接口定义（类和方法签名）
- 模块之间通过明确的公共接口通信，不允许直接访问内部实现
- 每个模块必须可以独立进行单元测试

**理由**：模块化设计确保代码可维护性，降低耦合度，便于未来扩展和重构。
独立的模块可以被单独测试、替换或升级而不影响其他部分。

### II. 用户体验至上 (User Experience First)

所有功能设计必须从用户体验角度出发，追求简洁、直观、高效。

**规则**：
- 快捷键响应时间必须 < 200ms
- 截图处理时间必须 < 500ms (1080p屏幕)
- 界面操作必须直观，核心功能不超过3次点击
- 错误提示必须清晰明确，提供解决方案而非技术术语
- 通知必须及时且信息完整（如：显示WSL路径而非仅"成功"）

**理由**：作为工具类软件，用户体验直接决定采用率。快速响应和直观操作
是基本要求，清晰的错误提示可以减少用户困惑和支持成本。

### III. 测试驱动开发 (Test-Driven Development)

核心功能模块必须编写单元测试，测试覆盖率目标 > 70%。

**规则**：
- 路径转换、剪贴板操作、配置管理等纯逻辑模块必须有完整单元测试
- 关键路径（截图→保存→转换→复制）必须有集成测试
- 测试必须覆盖正常场景和边界条件（空路径、特殊字符、权限不足等）
- 新功能开发时，先编写测试用例，确认失败后再实现功能（TDD）

**理由**：测试确保代码质量和稳定性。对于路径转换等核心功能，错误可能
导致用户数据丢失或工作流中断，因此必须通过完善测试保证正确性。

### IV. 性能与资源效率 (Performance & Resource Efficiency)

后台运行时必须保持低资源占用，不影响用户主要工作。

**规则**：
- 后台运行内存占用必须 < 50MB
- 空闲时CPU占用必须 < 1%
- 程序启动时间必须 < 3秒
- 截图文件必须支持可配置的清理策略，避免磁盘空间耗尽
- 日志文件必须支持轮转，防止无限增长

**理由**：作为常驻后台的工具，高资源占用会影响用户系统性能和体验。
合理的资源管理确保工具不会成为系统负担。

### V. 安全与隐私 (Security & Privacy)

必须明确权限需求，保护用户隐私，不收集不必要的数据。

**规则**：
- 管理员权限请求必须有明确说明（用于截取管理员窗口）
- 不得收集、上传或分享用户截图内容
- 配置文件和日志必须存储在本地，不涉及网络传输
- 临时截图文件的清理策略必须尊重用户选择
- 代码必须避免常见安全漏洞（如路径遍历、命令注入）

**理由**：截图可能包含敏感信息，隐私保护是用户信任的基础。明确的权限
说明和本地化数据处理符合最小权限原则。

### VI. 跨平台兼容性 (Cross-Platform Compatibility)

虽然当前版本针对Windows平台，但架构设计必须考虑未来跨平台扩展。

**规则**：
- 平台相关代码必须隔离在专门的模块中（如 `src/system/`）
- 核心逻辑（路径转换、配置管理等）必须与平台无关
- 文件路径处理必须使用跨平台方式（pathlib而非硬编码分隔符）
- 依赖库选择时优先考虑跨平台支持

**理由**：虽然v1.0专注Windows，但长期规划包括Linux和macOS支持。
提前做好架构隔离可以大幅降低未来移植成本。

### VII. 简洁性原则 (Simplicity - YAGNI)

避免过度设计，专注当前需求，遵循YAGNI (You Aren't Gonna Need It) 原则。

**规则**：
- 不实现未明确列入需求的功能
- 避免引入不必要的抽象层或设计模式
- 配置项保持最少必要集合，避免配置爆炸
- 优先使用标准库和成熟的第三方库，避免重复造轮子

**理由**：过度设计增加复杂度和维护成本。专注核心功能，快速交付MVP，
根据用户反馈迭代，比一开始构建复杂系统更高效。

## 开发标准

### 代码规范

- **Python代码风格**：严格遵循PEP 8规范
- **命名约定**：
  - 类名使用大驼峰 (PascalCase): `ScreenshotCapture`
  - 函数/方法使用小写下划线 (snake_case): `capture_screen()`
  - 常量使用大写下划线: `MAX_SCREENSHOT_SIZE`
- **文档字符串**：所有公共类和方法必须有docstring说明功能、参数、返回值
- **类型注解**：核心模块必须使用Python类型注解，提高代码可读性
- **代码格式化工具**：使用Black进行自动格式化
- **静态分析**：使用Flake8检查代码质量，无严重警告

### 日志与错误处理

- **日志级别使用规范**：
  - DEBUG: 详细诊断信息（仅开发调试）
  - INFO: 关键操作记录（程序启动、截图操作、配置更改）
  - WARNING: 可恢复的异常情况（权限不足但降级处理、配置项缺失使用默认值）
  - ERROR: 功能失败但程序可继续（截图失败、剪贴板操作失败）
- **错误处理原则**：
  - 所有外部操作（文件、剪贴板、注册表）必须有异常捕获
  - 错误信息必须包含上下文（如：失败的文件路径）
  - 向用户展示的错误必须友好且可操作

### 依赖管理

- **核心依赖**：PyQt5, Pillow, mss, pywin32, pynput
- **开发依赖**：pytest, pytest-cov, black, flake8, mypy
- **依赖版本管理**：requirements.txt中固定主版本号，允许次版本更新
- **新依赖引入原则**：
  - 必须评估许可证兼容性
  - 优先选择活跃维护的成熟项目
  - 避免引入功能重叠的库

## 治理规则

### 宪章修订流程

1. **提议修订**：任何开发者可提出修订建议，需说明理由和影响范围
2. **影响评估**：评估修订对现有代码、架构、流程的影响
3. **文档更新**：更新宪章文档，同步修改相关模板和指南
4. **版本号规则**：
   - MAJOR (X.0.0): 不兼容的原则移除或重新定义
   - MINOR (x.Y.0): 新增原则或重大扩展
   - PATCH (x.y.Z): 澄清、措辞优化、非语义改进

### 合规性审查

- **代码审查阶段**：检查代码是否符合核心原则和开发标准
- **架构决策**：重大架构变更必须评估与宪章原则的一致性
- **复杂度控制**：违反简洁性原则（如引入不必要的抽象）需明确说明必要性

### 例外处理

如确需违反宪章原则（如性能优化需要引入复杂度），必须：

1. 在设计文档中明确记录违反的原则
2. 说明为何必须违反以及评估的替代方案
3. 提供复杂度控制和未来简化的计划
